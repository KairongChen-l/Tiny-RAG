# 架构设计

## 整体架构设计

### 分层架构

系统采用**分层架构**，从上到下分为：

1. **HTTP API层**: 处理HTTP请求和响应
2. **业务逻辑层**: 核心业务模块
3. **数据访问层**: 向量存储和任务存储
4. **基础设施层**: 缓存、重试、限流等

### 模块化设计

系统采用**模块化设计**，每个模块职责单一、接口清晰：

```
ingestion → chunking → embedding → index
                                    ↑
retrieval ← prompt ← generation ←──┘
```

## 模块划分和职责

### 1. 文档处理模块

#### ingestion (文档摄取)
- **职责**: 解析各种格式的文档
- **输入**: 文件路径
- **输出**: 结构化的Document对象
- **特点**: 支持多格式、保留文档结构

#### chunking (文档分块)
- **职责**: 将文档切分为适合检索的chunks
- **输入**: Document对象
- **输出**: Chunk数组
- **特点**: 结构感知、语义分块、重叠机制

### 2. 向量化模块

#### embedding (向量嵌入)
- **职责**: 将文本转换为向量
- **输入**: 文本字符串
- **输出**: 向量数组
- **特点**: 多Provider、批量处理、缓存机制

#### index (向量存储)
- **职责**: 存储和检索向量
- **输入**: ChunkWithVector
- **输出**: SearchResult
- **特点**: 多后端支持、增量更新、版本控制

### 3. 检索和生成模块

#### retrieval (检索模块)
- **职责**: 从向量存储中检索相关文档
- **输入**: 用户查询
- **输出**: RetrievedChunk数组
- **特点**: 混合检索、查询重写、Reranking

#### prompt (提示词构建)
- **职责**: 组装LLM提示词
- **输入**: 查询和检索结果
- **输出**: Prompt对象
- **特点**: 引用格式化、Token截断、上下文组装

#### generation (LLM生成)
- **职责**: 调用LLM生成回答
- **输入**: Prompt对象
- **输出**: Response对象
- **特点**: 多Provider、流式响应、错误处理

### 4. 辅助模块

#### conversation (对话管理)
- **职责**: 管理多轮对话上下文
- **特点**: 消息管理、上下文窗口、对话摘要

#### job (异步任务)
- **职责**: 管理后台异步任务
- **特点**: Worker Pool、状态追踪、进度更新

#### api (HTTP API)
- **职责**: 提供RESTful API
- **特点**: 路由、中间件、错误处理

## 接口设计原则

### 1. 接口隔离原则 (ISP)

每个接口职责单一，避免臃肿：

```go
// ✅ 好的设计：职责单一
type Embedder interface {
    Embed(ctx context.Context, text string) ([]float32, error)
    EmbedBatch(ctx context.Context, texts []string) ([][]float32, error)
}

// ❌ 不好的设计：职责过多
type Embedder interface {
    Embed(...)
    Cache(...)
    Retry(...)
    Metrics(...)
}
```

### 2. 依赖倒置原则 (DIP)

依赖抽象而非具体实现：

```go
// ✅ 依赖接口
func NewRetriever(store VectorStore, embedder Embedder) Retriever

// ❌ 依赖具体实现
func NewRetriever(store *SQLiteStore, embedder *OpenAIEmbedder) Retriever
```

### 3. 开闭原则 (OCP)

对扩展开放，对修改关闭：

```go
// ✅ 通过注册表扩展，无需修改现有代码
registry.Register("new-provider", newProvider)

// ❌ 需要修改现有代码
if provider == "new-provider" {
    // 新逻辑
}
```

## 设计模式应用

### 1. 注册表模式 (Registry Pattern)

**应用场景**: 管理多个Provider

**实现**:
- `ParserRegistry`: 文档解析器注册表
- `EmbedderRegistry`: Embedding provider注册表
- `LLMRegistry`: LLM provider注册表

**优势**:
- 运行时注册，无需修改代码
- 支持多Provider切换
- 易于扩展新Provider

**示例**:
```go
registry := NewEmbedderRegistry()
registry.Register("openai", openaiEmbedder)
registry.Register("ollama", ollamaEmbedder)
registry.SetDefault("openai")
```

### 2. 策略模式 (Strategy Pattern)

**应用场景**: 可替换的算法

**实现**:
- 分块策略：结构感知、语义分块
- 检索策略：向量、BM25、混合
- 融合策略：RRF、Average、Max

**优势**:
- 算法可替换
- 易于测试
- 符合开闭原则

**示例**:
```go
type Chunker interface {
    Split(doc *Document) ([]Chunk, error)
}

// 不同策略实现同一接口
semanticChunker := NewSemanticChunker(config)
embeddingChunker := NewEmbeddingSemanticChunker(config, embedder)
```

### 3. 适配器模式 (Adapter Pattern)

**应用场景**: 接口适配

**实现**:
- `VectorStore`接口的多种实现（SQLite、Qdrant）
- `Cache`接口的多种实现（内存、Redis）

**优势**:
- 统一接口，多种实现
- 易于切换后端
- 符合依赖倒置原则

**示例**:
```go
type VectorStore interface {
    Store(ctx context.Context, chunks []ChunkWithVector) error
    Search(ctx context.Context, query []float32, opts SearchOptions) ([]SearchResult, error)
}

// 不同实现
sqliteStore := NewSQLiteStore(db)
qdrantStore := NewQdrantStore(client)
```

### 4. Worker Pool 模式

**应用场景**: 并发任务处理

**实现**:
- `job.Queue`: 任务队列和Worker Pool

**优势**:
- 控制并发数
- 资源复用
- 提高吞吐量

**示例**:
```go
queue := NewQueue(QueueConfig{
    Workers:   10,
    QueueSize: 100,
}, store, handler, logger)
```

### 5. 装饰器模式 (Decorator Pattern)

**应用场景**: 功能增强

**实现**:
- `CachedEmbedder`: 为Embedder添加缓存
- 中间件：为Handler添加日志、限流等

**优势**:
- 功能组合
- 不修改原有代码
- 灵活配置

**示例**:
```go
baseEmbedder := NewOpenAIEmbedder(config)
cachedEmbedder := NewCachedEmbedder(baseEmbedder, cache)
```

## 扩展性设计

### 1. 新文档格式支持

**扩展点**: `Parser`接口

**步骤**:
1. 实现`Parser`接口
2. 注册到`ParserRegistry`
3. 无需修改其他代码

**示例**:
```go
type CustomParser struct{}

func (p *CustomParser) Parse(ctx context.Context, path string) (*Document, error) {
    // 实现解析逻辑
}

registry.Register(&CustomParser{})
```

### 2. 新存储后端支持

**扩展点**: `VectorStore`接口

**步骤**:
1. 实现`VectorStore`接口
2. 在配置中添加provider选项
3. 工厂方法创建对应实例

### 3. 新LLM Provider支持

**扩展点**: `LLM`接口

**步骤**:
1. 实现`LLM`接口
2. 注册到`LLMRegistry`
3. 配置文件中添加配置项

### 4. 新检索策略支持

**扩展点**: `Retriever`接口

**步骤**:
1. 实现`Retriever`接口
2. 在检索流程中集成
3. 支持配置切换

## 可维护性设计

### 1. 模块边界清晰

- 每个模块职责单一
- 模块间通过接口交互
- 避免循环依赖

### 2. 错误处理统一

- 统一的错误类型
- 详细的错误信息
- 错误分类（可重试/不可重试）

### 3. 日志和监控

- 结构化日志（zap）
- Prometheus指标
- 请求追踪（RequestID）

### 4. 配置管理

- 统一的配置结构
- 环境变量支持
- 配置验证

### 5. 测试覆盖

- 单元测试
- 集成测试
- 端到端测试

## 数据流设计

### 1. 文档摄取流程

```
文件 → Parser → Document → Chunker → Chunks → Embedder → Vectors → Index
```

### 2. 查询流程

```
Query → Embedder → Vector → Index → Chunks → Reranker → Prompt → LLM → Answer
```

### 3. 异步任务流程

```
API → JobQueue → Worker → Handler → 业务逻辑 → 状态更新
```

### 1. 异步处理

- 文档摄取异步化
- 不阻塞API响应
- Worker Pool并发处理

### 2. 批量操作

- Embedding批量处理

### 3. 缓存机制

### 1. 错误处理

- 重试机制（指数退避）
- 错误分类（可重试/不可重试）
- 详细错误信息

### 2. 熔断保护

- 防止级联失败

### 3. 限流控制

- API限流
- Provider限流
- 防止资源耗尽

### 4. 超时控制

- 所有外部调用都有超时
- 可配置超时时间

### 5. 优雅关闭

- 信号处理
- 资源清理

## 总结

本系统采用**模块化、接口化、可扩展**的架构设计，通过设计模式的应用和清晰的模块边界，实现了高内聚、低耦合的系统架构。系统支持水平扩展、多Provider切换、插件化扩展，同时具备完善的错误处理、监控和测试覆盖，是一个生产级的RAG系统实现。
